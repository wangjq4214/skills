# Historical evidence

Use the sources and retrieval capabilities actually available in the host. Do not assume a session directory, API, tree format, or complete transcript. If history is inaccessible, ask for the relevant export or continue with available evidence and state the limitation; do not build or install an adapter as an implicit part of the retrospective.

## Bound retrieval

Establish the requested project, time range, and question. Narrow by metadata and inexpensive searches first, then inspect relevant execution sequences rather than loading every transcript into context. Use activity within the requested period, not just session creation time, when available.

Keep source locators with excerpts: session/file identifier and entry IDs, timestamps, or line ranges. Include enough surrounding instructions, actions, results, and feedback to evaluate a candidate; a search hit or summary alone is not a confirmed incident. Report how many sources were found, screened, and deeply inspected, plus skipped, inaccessible, or truncated material. A request covering all sessions cannot silently become a sample; disclose incomplete coverage or agree on a narrower scope.

## Reconstruct and correlate

Where histories branch, follow the relevant ancestry instead of treating file order as one conversation. Separate observed raw history from what the agent could see at the decision point: compaction, context edits, and branch changes may alter the latter. Inspect original evidence when available; if effective context or the applicable instruction version cannot be recovered, mark that attribution limit rather than reconstructing it from current files.

Count independent incidents, not every correction, retry, branch, or copied/forked transcript. Use lineage and shared source entries where available; otherwise explain uncertain overlap rather than claiming an exact recurrence count. Preserve links to distinct occurrences when grouping a pattern. Similar wording, tool names, or outcomes are candidate signals, not proof of a common root cause.

Search comparable successful executions as well as failures when investigating conditions or prevalence. Failure-focused retrieval can establish examples, not a failure rate. A single serious incident may warrant prevention without being called recurrent.

For before/after or model comparisons, identify observed versions/configuration, comparable task types, and the number of relevant opportunities in each group. Account for differences in scope, permissions, tools, model, and task difficulty where known. Without comparable denominators and conditions, report descriptive observations, not a causal improvement claim. Do not infer a skill was active merely because it exists today, or attribute a response to a model solely from a session-wide label when models may change mid-session.

Keep findings lightweight and in memory: issue and impact, source locators, independent occurrences and overlap uncertainty, cause hypothesis/confidence, proposed remedy, and verification status. No fixed taxonomy, persistent index, or clustering system is required.
